# Задание 10. Миграция на Cassandra: модель данных, стратегии репликации и шардирования

## Задание 10.1: Определение критически важных данных

### Критически важные данные с точки зрения целостности и скорости обработки:

1. **Корзины (carts)**:
   - **Критичность**: Высокая в пиковые периоды
   - **Характеристики**: Очень высокая частота чтения/записи (до 50K запросов/с), низкая задержка для пользовательского опыта
   - **Требования к целостности**: Умеренные (временная потеря корзины менее критична, чем потеря заказа)

2. **Пользовательские сессии**:
   - **Критичность**: Средняя/высокая для пользовательского опыта
   - **Характеристики**: Высокая частота чтения/записи, временные данные
   - **Требования к целостности**: Низкие (сессию можно восстановить при потере)

3. **История заказов (для чтения)**:
   - **Критичность**: Высокая для пользовательского доверия
   - **Характеристики**: Высокая нагрузка на чтение, низкая на запись (только агрегация из основной системы)
   - **Требования к целостности**: Высокие для точности отображения

4. **Заказы (orders)** и **Товары (products)**:
   - **Критичность**: Максимальная для бизнес-процессов
   - **Характеристики**: Требуют строгой согласованности для финансовых операций и остатков
   - **Требования к целостности**: Критические (нельзя допустить перепродажу или потерю заказа)

### Обоснование выбора данных для Cassandra:

**Cassandra идеально подходит для:**

1. **Корзины (carts)**:
   - **Масштабируемость**: Cassandra обеспечивает линейное масштабирование без полного перераспределения данных при добавлении узлов, что решает проблему высокой задержки при масштабировании в MongoDB
   - **Геораспределённость**: Данные можно реплицировать между дата-центрами для снижения latency для пользователей в разных регионах
   - **Скорость записи/чтения**: Cassandra оптимизирована для высокочастотных операций записи с настраиваемой согласованностью
   - **Целостность данных**: Достаточно eventual consistency для корзин, так как временная несогласованность менее критична

2. **Пользовательские сессии**:
   - Временные данные идеально подходят для TTL-механизмов Cassandra
   - Высокая частота доступа требует минимальной задержки
   - Leaderless-репликация обеспечивает высокую доступность даже при отказе узлов

3. **История заказов (только для чтения)**:
   - Высокая нагрузка на чтение оптимально обрабатывается Cassandra
   - Данные можно агрегировать из основной транзакционной системы
   - Требования к согласованности ниже, чем для активных заказов

**Для заказов и остатков товаров Cassandra не подходит:**
- Требуется строгая согласованность для финансовых операций
- Необходимы атомарные транзакции между несколькими сущностями
- Риск перепродажи при eventual consistency неприемлем

## Задание 10.2: Концептуальная модель данных для Cassandra

### 1. Корзины (carts)

```sql
-- Основная таблица для доступа по пользователю
CREATE TABLE carts_by_user (
    bucket int,                -- Бакет для предотвращения горячих партиций
    user_id uuid,              -- ID пользователя (NULL для гостей)
    session_id text,           -- ID сессии для гостей
    cart_id timeuuid,          -- Уникальный ID корзины
    items list<frozen<cart_item>>, 
    status text,               -- active, ordered, abandoned
    created_at timestamp,
    updated_at timestamp,
    expires_at timestamp,
    PRIMARY KEY ((bucket, user_id, session_id), cart_id)
) WITH CLUSTERING ORDER BY (cart_id DESC)
  AND default_time_to_live = 2592000  -- 30 дней
  AND compaction = {'class': 'TimeWindowCompactionStrategy', 'compaction_window_size': 1, 'compaction_window_unit': 'DAYS'};
```

```sql
CREATE TYPE cart_item (
    product_id uuid,
    quantity int,
    price decimal,
    name text
);
```

```sql
-- Дополнительная таблица для доступа по сессии (для гостей)
CREATE TABLE carts_by_session (
    bucket int,
    session_id text,
    cart_id timeuuid,
    user_id uuid,
    items list<frozen<cart_item>>,
    status text,
    created_at timestamp,
    updated_at timestamp,
    expires_at timestamp,
    PRIMARY KEY ((bucket, session_id), cart_id)
) WITH CLUSTERING ORDER BY (cart_id DESC)
  AND default_time_to_live = 2592000
  AND compaction = {'class': 'TimeWindowCompactionStrategy', 'compaction_window_size': 1, 'compaction_window_unit': 'DAYS'};
```

**Partition key:** `(bucket, user_id, session_id)`  
**Кластерный ключ:** `cart_id`  
**Бакеты:** `bucket = murmur3(userId) % 16` для равномерного распределения

### 2. Пользовательские сессии

```sql
CREATE TABLE user_sessions (
    bucket int,
    session_id text,
    user_id uuid,
    data map<text, text>,      -- Произвольные данные сессии
    last_activity timestamp,
    created_at timestamp,
    expires_at timestamp,
    PRIMARY KEY ((bucket, session_id))
) WITH default_time_to_live = 86400  -- 24 часа
  AND compaction = {'class': 'TimeWindowCompactionStrategy', 'compaction_window_size': 1, 'compaction_window_unit': 'HOURS'};
```

**Partition key:** `(bucket, session_id)`  
**Бакеты:** `bucket = murmur3(session_id) % 16`

### 3. История заказов (только для чтения)

```sql
-- Доступ по пользователю
CREATE TABLE order_history_by_user (
    bucket int,
    user_id uuid,
    order_date timestamp,
    order_id uuid,
    total_amount decimal,
    status text,
    geozone text,
    items list<frozen<order_item>>,
    PRIMARY KEY ((bucket, user_id), order_date, order_id)
) WITH CLUSTERING ORDER BY (order_date DESC, order_id DESC);
```

```sql
-- Детали отдельного заказа
CREATE TABLE order_details (
    order_id uuid,
    user_id uuid,
    order_date timestamp,
    items list<frozen<order_item>>,
    shipping_address frozen<address>,
    billing_address frozen<address>,
    total_amount decimal,
    status text,
    geozone text,
    PRIMARY KEY (order_id)
);
```

```sql
-- Аналитика по геозонам
CREATE TABLE orders_by_geozone (
    geozone text,
    order_date timestamp,
    order_id uuid,
    user_id uuid,
    total_amount decimal,
    status text,
    PRIMARY KEY ((geozone), order_date, order_id)
) WITH CLUSTERING ORDER BY (order_date DESC, order_id DESC);
```

```sql
CREATE TYPE order_item (
    product_id uuid,
    name text,
    quantity int,
    price decimal
);

CREATE TYPE address (
    street text,
    city text,
    postal_code text,
    country text
);
```

### Обоснование модели:

1. **Предотвращение горячих партиций**:
   - Использование бакетов (`bucket`) для равномерного распределения нагрузки
   - Особенно важно для популярных пользователей или геозон
   - Бакеты рассчитываются на клиенте по алгоритму `murmur3(key) % N`

2. **Минимизация влияния решардинга**:
   - Cassandra использует consistent hashing (виртуальные узлы), поэтому при добавлении нового узла перемещается только 1/N данных
   - В отличие от MongoDB, где полное перераспределение вызывает просадку latency
   - Virtual Nodes (vnodes) обеспечивают автоматический баланс при изменении топологии

3. **Оптимизация под паттерны доступа**:
   - Дублирование данных в разных таблицах для разных паттернов запросов
   - Кластерные ключи обеспечивают эффективную фильтрацию и сортировку без сканирования всей партиции
   - TWCS для таблиц с TTL оптимизирует сборку мусора

4. **Масштабируемость при пиковых нагрузках**:
   - Модель выдерживает до 50K запросов/сек. для корзин без увеличения задержки
   - Добавление узлов линейно увеличивает пропускную способность без просадки latency

## Задание 10.3: Стратегии обеспечения целостности данных

### Стратегии восстановления целостности:

1. **Hinted Handoff**:
   - Хранение "подсказок" о записях при недоступности узлов
   - Автоматическая доставка при возвращении узла в строй
   - Настраиваемый TTL для hints

2. **Read Repair**:
   - Обнаружение и исправление расхождений при чтении данных
   - Работает как в фоновом режиме, так и во время запросов
   - Настраиваемая вероятность запуска

3. **Anti-Entropy Repair**:
   - Фоновый процесс сравнения данных на всех репликах с использованием Merkle trees
   - Полное восстановление согласованности между репликами
   - Требует значительных ресурсов, запускается в периоды низкой нагрузки

### Выбор стратегий по сущностям:

| Сущность | Hinted Handoff TTL | Read Repair Chance | Anti-Entropy Repair | Consistency Level | Обоснование |
|----------|-------------------|-------------------|---------------------|-------------------|-------------|
| **Корзины** | 3 часа | 0.2 (20%) | Ежедневно в 02:00-06:00 | QUORUM / QUORUM | Баланс между целостностью и производительностью. Временная несогласованность допустима, но потеря данных нежелательна. |
| **Сессии** | 1 час | 0 (отключен) | Еженедельно | ONE / ONE | Максимальная производительность в ущерб согласованности. Сессии временные и могут быть восстановлены. |
| **История заказов** | 3 часа | 1.0 (100%) | Ежедневно | ALL (запись) / QUORUM (чтение) | Максимальная целостность. Пользователи ожидают точной информации о своих заказах. |

### Дополнительные стратегии:

1. **Speculative Retry**:
   ```yaml
   speculative_retry: "99PERCENTILE"
   ```
   - Запускать повторные запросы к другим репликам при медленном ответе
   - Критически важно для поддержания низкой задержки во время пиковых нагрузок

2. **Tunable Consistency для разных операций**:
   - Для добавления товара в корзину: `LOCAL_QUORUM`
   - Для просмотра истории заказов: `LOCAL_QUORUM`
   - Для просмотра деталей заказа: `QUORUM`

3. **Стратегия репликации**:
   ```sql
   CREATE KEYSPACE mobile_world 
   WITH REPLICATION = {
     'class': 'NetworkTopologyStrategy',
     'dc1': 3,  -- Основной дата-центр
     'dc2': 2   -- Резервный дата-центр для гео-репликации
   };
   ```

### Компромиссы между latency и согласованностью:

1. **Корзины**:
   - **Компромисс**: 80% согласованности при latency < 10ms
   - **Обоснование**: Пользователь скорее уйдет при высокой задержке, чем из-за временной несогласованности корзины
   - **Сценарий**: При пиковой нагрузке в "черную пятницу" система сохраняет отзывчивость за счет частичной согласованности

2. **Сессии**:
   - **Компромисс**: 60% согласованности при latency < 5ms
   - **Обоснование**: Потеря сессии приведет к перезаполнению данных, но пользователь останется в системе из-за низкой задержки
   - **Сценарий**: При высокой нагрузке временно отключается read repair для минимизации latency

3. **История заказов**:
   - **Компромисс**: 99.9% согласованности при latency < 50ms
   - **Обоснование**: Несогласованность истории заказов подрывает доверие пользователей
   - **Сценарий**: Даже в пиковые периоды приоритет отдается согласованности, так как это read-heavy операция
